# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`vector-algorithms` is a Haskell library of efficient in-place sorting (and related) algorithms over mutable vectors from the `vector` package. Supports GHC versions as listed in the cabal file (`tested-with` in `vector-algorithms.cabal`), so avoid language features or library APIs that break older compilers.

## Commands

```sh
cabal build                      # build library (tests are enabled by default via cabal.project)
cabal test                       # run QuickCheck property suite (output shown directly)
cabal bench simple-bench         # build and run the benchmark
cabal run simple-bench -- --help # benchmark options: -A ALGO, -n NUM_ELEMS, -k PORTION
cabal build -f InternalChecks -f UnsafeChecks   # enable extra internal/unsafe assertions
```

The test suite (`tests/properties/Tests.hs`) is a single executable whose `main` calls a sequence of `check_*` groups; there is no CLI test selection. To run one group, either temporarily trim `main`, or use `cabal repl properties` and evaluate e.g. `check_Int_sort` directly.

CI is generated by `haskell-ci` (config in `cabal.haskell-ci`, output in `.github/workflows/haskell-ci.yml`). Don't hand-edit the workflow; regenerate it with `haskell-ci regenerate` after changing `tested-with`.

## Architecture

- Each algorithm lives in its own module under `src/Data/Vector/Algorithms/` (Intro, Merge, Heap, Tim, Insertion, Radix, AmericanFlag, Optimal, Search). All operate on the generic mutable interface `Data.Vector.Generic.Mutable.MVector v e` in any `PrimMonad m`, so they work for boxed, unboxed, storable and primitive vectors.
- Modules follow a consistent API layering: `sort = sortBy compare`, `sortBy cmp a = sortByBounds cmp a 0 (length a)`, plus `sortUniq`/`sortUniqBy` (sort and return a deduplicated slice), and where applicable `select*` and `partialSort*` families. New algorithms/variants should follow the same `X` / `XBy` / `XByBounds` pattern.
- Algorithms compose: Intro sort falls back to Heap sort and finishes small ranges with Insertion and the `Optimal` sorting networks (hand-unrolled sorts for 2–4 elements); Merge uses Insertion/Optimal for small runs; Tim uses Insertion for minimum runs and `Search`'s galloping searches for merging. Radix and AmericanFlag are key-based sorts driven by their own type classes (`Radix`, `Lexicographic`) rather than a `Comparison`.
- `Data.Vector.Algorithms.Common` (internal, not exposed) holds shared helpers: the `Comparison` type, `copyOffset`, `midPoint`, bucket counting, and `uniqueMutableBy` used by all `sortUniq` implementations.
- `Data.Vector.Algorithms` (top-level) provides immutable-vector conveniences like `nub`/`nubBy`, built on `Intro.sortUniqBy` and a `bitvec` bit-set.
- Performance depends heavily on specialisation: exported functions are marked `{-# INLINE #-}` so they specialise at the call site's vector type and comparison. Removing or weakening INLINE pragmas is a performance regression even if tests pass (see recent commits fixing missing INLINEs on `sort`, `sortUniq`, `nub`).
- Compound `Lexicographic` instances must keep the bucket sequence order-consistent with `Ord`. The pair instance emits a separator bucket (0, with the first component's buckets shifted up by 1) where the first component ends; without it, a variable-extent first component such as `ByteString` runs into the second component's key and sorts wrongly. The pair tests in `check_flag_compound` cover this.
- `include/vector.h` provides CPP macros (bounds/unsafe/internal checks) toggled by the `BoundsChecks`, `UnsafeChecks` and `InternalChecks` cabal flags.
- `src/Data/Vector/Algorithms/Combinators.hs` and `bench/simple/RadSieve.hs` are not listed in the cabal file and are not built.

## Tests

The suite in `tests/properties/` takes about 30 seconds.

- `Properties.hs` defines the properties; `Tests.hs` instantiates them per algorithm using rank-N wrapper newtypes (`WrapAlgo`, `WrapSizeAlgo`, `WrapUniq`, ...). When adding an algorithm or variant, add it to the relevant lists in `Tests.hs` (including the vector-type and large-input groups).
- Prefer model-based properties: compare against `Data.List` (`sort`, the stable `sortBy`, `M.keys . toBag` for unique elements), which checks sortedness, permutation and stability in one equality. Avoid `prop_sorted`/`stable` on large inputs; they are slow.
- QuickCheck's default size keeps vectors under ~100 elements, which never reaches Tim sort's merging (it insertion sorts below 64) or deep introsort/merge levels. `Util.hs` has generators for this: `LargeVec` (64–5000 elements in named shapes: few-distinct, sorted runs, organ pipe, …), `BoundsCase` (a vector plus a sub-range `[l, u)` and count `k`, for `…ByBounds`, select, and heap operations; properties also check elements outside the range are unchanged) and `SearchCase` (a sorted `BoundsCase` plus a key). Their `shrink`s cut counterexamples down to a few elements; keep that working when changing them.
- `Adversary.hs` builds worst-case inputs with McIlroy's quicksort adversary and counts comparisons, used to check introsort stays within 6 n lg n (i.e. its heap sort fallback works). Its comparisons are impure (`unsafePerformIO`), so the module is compiled with `-fno-cse -fno-full-laziness`; keep such code there.
- `Optimal.hs` exhaustively checks the 2–4 element sorting networks, both at consecutive offsets and scattered, out-of-order indices.
- `Tests.hs` shadows `quickCheck`/`quickCheckWith` with versions that count failures, so the suite exits non-zero if any property fails. Use those (not `Test.QuickCheck`'s) for new groups, or failures won't fail CI.
- Insertion sort is quadratic: only test it on small vectors, not `LargeVec`.
- To check that a new test can actually fail, temporarily break the library (e.g. an off-by-one), run `cabal test`, look for `*** Failed!` lines and the `N properties failed` summary, then `git checkout` the source file.
